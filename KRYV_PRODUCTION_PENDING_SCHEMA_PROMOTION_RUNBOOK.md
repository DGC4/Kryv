# Kryv Production-Pending Schema Promotion Runbook

## Status and Authority Boundary

> **All migrations in this runbook are source-controlled and isolated-branch validated only. No production promotion has occurred, and this document does not authorize one.**

An **authorized operator** must provide a separate explicit approval before any migration in this runbook is executed against the Neon production branch. Source control, an isolated-branch validation record, and a green application build are necessary safeguards; they are not production authorization.

Advertising delivery remains hard-disabled (`AD_DELIVERY_RUNTIME_ENABLED = false`). Promoting the advertising-related tables below **must not** be interpreted as approval to enable ad decisions, ad serving, impression APIs, client measurement, budget consumption, or provider withdrawals.

## Required Promotion Sequence

| Step                    | Required action                                                                                                                                                                      | Stop condition                                                                   |
| ----------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------- |
| 1. Approval             | Record the authorized production approval, exact migration set, operator, maintenance window, and rollback owner.                                                                    | Do not proceed without explicit approval.                                        |
| 2. Freshness review     | Compare the production schema and relevant data conditions with the isolated validation evidence. If the baseline has drifted, validate on a fresh isolated branch before promotion. | Any schema or data drift that invalidates the record.                            |
| 3. Production preflight | Capture production row counts and duplicate checks required by `0027` and `0028`; assess table volume and locking risk for `0021`.                                                   | Duplicate rows, unresolved data quality issue, or unacceptable operational risk. |
| 4. Execute              | Run ordinary additive DDL only in the approved execution context. Run every `CREATE INDEX CONCURRENTLY` statement independently **outside a transaction**.                           | Migration runner wraps concurrent DDL in a transaction or reports an error.      |
| 5. Verify               | Query PostgreSQL catalogs and constraints to confirm names, predicates, key order, and validity. Confirm application health, error rates, and the relevant bounded query paths.      | Missing or mismatched catalog entry, failing health check, or elevated errors.   |
| 6. Monitor              | Monitor the approved window for database contention, query latency, notification delivery, profile mutations, and Watch/Cinema access behavior.                                      | Any material regression; stop further promotion and follow the incident owner.   |

## Non-Negotiable Safeguards

The promotions must preserve the following conditions. `0024` through `0028` contain `CREATE INDEX CONCURRENTLY` statements and therefore **must not be executed inside a transaction**. The migration record and this runbook both retain an explicit no-production-promotion boundary until separate approval occurs. Production schema access must continue to use the approved Neon operation workflow; no application code deployment is a substitute for database promotion authorization.

For the two partial unique indexes, the operator must run the documented production duplicate preflights immediately before the approved build. For the Watch maturity migration, the operator must decide whether to split the readiness index into a concurrent post-DDL step when current production table size makes that operationally safer. For all advertising-related work, the runtime hard-disable and the separate launch gates remain in force after schema promotion.

## Evidence to Attach to an Approved Change Record

The approval record should include the executed SQL statements, transaction boundaries, timestamps, executing operator, production `pg_indexes`/constraint output, duplicate-preflight output where applicable, release commit SHA, application health evidence, and a monitoring handoff. Do not attach database credentials, private payout destinations, raw viewer data, signed receipts, or provider secrets.
