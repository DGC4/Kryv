# Kryv advertising-system audit — working notes

## Existing system discovered

Kryv already contains an advertising control plane and corresponding frontend/admin surfaces. The system is intentionally **hard-disabled** in the runtime (`AD_DELIVERY_RUNTIME_ENABLED = false`) and through application status reporting. This is an appropriate default while consent, creative review, delivery measurement, rate limiting, operator kill switch, and reconciliation evidence are incomplete.

The current model includes `ad_campaigns`, `ad_creatives`, campaign rules/breaks, `ad_impressions`, consent/inventory structures, and `ad_campaign_fundings`. The owner-facing control plane supports promotional flights and crypto-funded advertiser campaigns, but campaign creation, funding invoices, approval, and delivery paths are explicitly blocked while the delivery gate is closed.

## Current safeguards observed

1. Paid delivery requires signed crypto-funding confirmation, owner approval, active rule, active creative, and an active delivery window.
2. Promotional flights require owner approval, explicit end time, active rule, and active creative.
3. The decision route returns no decision when campaign state, window, funding, promotion approval, creative, or serving context does not pass validation.
4. Campaign/funding/approval actions are owner-facing and audit logged.
5. The operator UI warns that advertising delivery, invoices, and approval remain hard-disabled until consent, creative review, measurement, and kill-switch controls are deployed together.
6. Privacy and safety screens state that advertising delivery is currently disabled and must be separately activated with the required controls.

## Implication for later work

Do **not** replace this system with a generic ad widget. Extend it only after Neon schema parity is confirmed and the missing delivery safeguards are defined: surface-specific placement policy, frequency caps, viewability/completion measurement, bot/fraud signals, content suitability, profile/maturity exclusion, privacy consent, advertiser/creative review status, decision idempotency, audit trail, operator kill switch, and reconciled billing/delivery reporting. No live campaign, invoice, withdrawal, custody, or ad delivery should be activated as part of the UI/product work.

## Production Neon parity review — 2026-08-20

A read-only review of the connected Neon production project (`kryv`, default branch) confirms that the required advertising, consent, profile, and hardened identity objects are present. The production table catalog contains `ad_campaigns`, `ad_creatives`, `ad_rules`, `ad_breaks`, `ad_impressions`, `ad_campaign_fundings`, `ad_revenue_movements`, `consent_preferences`, `consent_receipts`, `viewer_profiles`, `platform_roles`, `user_sessions`, and `users`.

The original progress summary referred generically to a `platform_sessions` concept. The source-of-truth repository name is actually **`user_sessions`**, which the production schema matches. It contains an opaque-session identifier, one-way token hash, user association, session-version binding, expiry, last-seen, revocation information, hashed IP context, user-agent context, and the unique/indexed controls declared in `lib/db/src/schema/auth.ts`. The production `users` table includes `session_version`, and production `platform_roles` provides explicit revocable role grants. This verifies that the 0020 identity/session hardening was applied under the actual repository naming convention.

Production `ad_campaigns` matches the repository model for advertiser identity, owner approval, campaign state/window, funding mode/status, budget accounting, creator-share basis points, targeting, and frequency policy. The bulk metadata inspection also confirmed column-level coverage for the campaign, creative, rule, break, impression, funding, revenue movement, consent, viewer-profile, role, session, and user objects listed above. No missing advertising-control-plane or identity-hardening table was observed.

| Control area | Current verified state | Implementation conclusion |
|---|---|---|
| Global serving gate | `AD_DELIVERY_RUNTIME_ENABLED = false`; the decision endpoint returns `ads_delivery_disabled` before any candidate lookup | Preserve the fail-closed state throughout all visual/UI work. |
| Free-tier surface scope | The decision request accepts `live`, `watch`, `cinema`, and `clip`; rule/break schema stores surface | Add an explicit server-side entitlement resolver so the three required free-tier surfaces are consistently evaluated, without enabling delivery. |
| Campaign eligibility | Active campaign, delivery window, funding mode/status, owner-approved rule linkage, and active creative are checked | Keep these checks and add explicit reviewed-creative/advertiser disclosure/safety metadata before any future activation. |
| Profiles | A supplied profile is verified to belong to the authenticated account before it can participate in an ad decision | Extend this into a signed active-profile grant so the API never trusts a client-selected profile ID alone. |
| Consent | The current route requires `ads_personalization` consent whenever a signed-in user exists | This is conservative but incomplete: define a deliberate contextual/no-measurement policy for users who decline, and ensure all uses of consent are server-resolved. |
| Frequency | Campaign policy JSON and live rule spacing/pod controls exist in the data model | No atomic impression-frequency evaluation is currently present in the decision route. Add an idempotent, concurrency-safe cap evaluator before delivery can be considered. |
| Measurement | `ad_impressions` stores requested/qualified/completed/failure state; no visible event-recording route was found in `ads.ts` | Add only a signed, narrow, idempotent event contract behind the global gate; prohibit client-supplied revenue/qualification claims. |
| Creator controls | Live owner can schedule, trigger, or defer only when the rule permits, but endpoint is blocked by the global gate | Retain owner checks, add audit logging and spacing/cap enforcement before enabling a future creator-initiated break feature. |
| Funding and allocation | Campaign funding and ad revenue movement tables exist, while delivery is disabled | Do not connect visual placement work to funding, payout, or allocation execution. Any accounting must be driven only by qualified, reconciled delivery events. |
