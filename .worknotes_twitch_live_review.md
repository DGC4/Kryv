# Twitch Live review working notes

**Scope:** Non-intrusive observation of Twitch’s public desktop home in the connected browser. No chat messages, follows, subscriptions, Bits, donations, purchases, or ad-feedback submissions were made.

## Discovery and navigation observations

Twitch presents a persistent header with Following, Browse, search, notifications/messages, a Bits promotion, and an explicit **Get Ad-Free** affordance. The desktop surface combines a collapsible followed-channel left rail, a featured-player module, topic/category discovery, recommendation rails, and a bottom promotional banner. The structural distinction between the global navigation, active live context, and current promotional state remains visible while browsing.

The live cards communicate primary decision-making facts: creator identity, stream title, category, language/tags, live state, and current viewers. The home surface separately groups personalized channels, a broader “What’s hot” module, and categories. The category cards combine viewer totals and topic taxonomy, with relevant genre labels beside game titles. This supports quick content selection without requiring a separate search step.

## Advertising and entitlement observations

An advertising unit was visibly labelled **Ad** in the discovery area. Its media interface exposed ad-specific controls including pause, mute, captions, a visible elapsed/remaining time state (`0:00` in this observation), a **Learn More** action, a disclosure/feedback control labelled **Leave feedback for this Ad**, and a Show more control. The commercial card appeared as a dedicated placement rather than an unlabelled organic live card.

Twitch’s header displayed **Get Ad-Free**, making a paid entitlement alternative visible in the global frame. The transferable product principle for Kryv is not the specific commercial model; it is that any free-tier advertising policy must be paired with clear, non-deceptive disclosure and a server-authoritative entitlement outcome. On Kryv, only the server should decide an account/profile’s free-tier ad eligibility for Cinema, Watch, and Live. The client must never infer or toggle ad eligibility locally.

## Player and accessibility observations

The featured player surface exposed standard playback controls with keyboard hints: play, mute, volume slider, settings, and full-screen. The UI also gave an explicit label for the active channel, category, language tag, and viewer count beside the playback stage. These patterns reinforce the need for an owned Kryv player capability contract: controls are rendered only when the underlying provider can honor the operation, and controls must remain keyboard- and touch-operable.

## Initial transferable requirements for Kryv Live

| Area | Original Kryv implementation requirement |
|---|---|
| Guide | Build a collapsible `LiveGuide` with followed/recommended channel state that does not block the primary player at narrow widths. |
| Cards | Include live status, creator, title, category, language, viewer count, maturity/content-safety state, and an accessible contextual-menu trigger. |
| Discovery | Maintain separate personalized, editorial/currently popular, category, clip, and replay modules, each with explicit loading/error/empty states. |
| Ads | Build a visually distinct `AdSlot` with disclosure, advertiser identity, content-type label, duration/skip state when policy allows, caption/mute controls for video, feedback/report entry, and a safe external-CTA confirmation/allowlist boundary. Keep it behind the existing hard-disabled server gate. |
| Entitlement | Resolve free-tier versus eligible ad-free state server-side from account entitlement plus active-profile policy, and include the surface (`cinema`, `watch`, `live`) in every decision. |
| Player | Implement only validated capabilities and keep playback, chat, commercial controls, and creator-support actions separate. |
| Accessibility | Use labelled controls, keyboard shortcuts, focus management, captions support, persistent disclosure, and no hover-only commercial disclosure or skip mechanism. |

## Public live-channel observations

The observed public channel uses a three-column desktop structure: a persistent followed/live-channel guide, a large central player stage, and an independently scrollable chat pane. The primary stream identity row places live state, creator identity, category/tags/language, stream uptime, viewer count, and creator support actions near the player. Follow, **Gift a Sub**, and **Subscribe** are grouped but remain visually distinct from playback controls and chat participation.

The player exposed labelled operations for play, mute/unmute, volume, settings, theatre mode, and full-screen, including visible keyboard shortcuts. The chat pane showed an explicit **Followers-Only Chat** state before the composer, plus separate controls for community context, cheering, emotes, balances, Drops, and chat settings. The observed channel also presents transparent creator-progress modules, including follower, subscription, and Bits goals. These are useful engagement patterns but should only be implemented on Kryv with clearly labelled goals, abuse-resistant counter updates, and privacy-safe aggregation.

### Further Kryv Live requirements

| Area | Original Kryv requirement |
|---|---|
| `ChatAccessState` | The server returns an explicit mode and reason before the composer activates, covering public, follower-delayed, subscriber-only, verified-account, account-age, slow mode, timed-out, banned, and creator/moderator permissions. |
| Creator support | Keep following, subscription, gifts, tips, and any future creator rewards as isolated user-initiated flows. They must never be invoked by the player, chat composer, advertising controls, or an automatic retry. |
| Engagement goals | Treat goal counters as separately authorized, rate-limited, server-derived aggregates. Never expose private payment state, exact personal balances, or raw account identifiers in the public view. |
| Chat resilience | Establish independent error/reconnect states for chat and player. A player failure must retain reporting and chat safety controls; a chat outage must not stop playback. |
| Live layout | Preserve `LiveGuide`, `KryvPlayer`, `StreamIdentityPanel`, `CreatorSupportPanel`, and `LiveChat` as discrete modules with responsive stacking/tab behavior, not one coupled page component. |
| Free-tier ads | A future Live `AdSlot` must live at an explicit, policy-eligible placement boundary and be omitted entirely if no signed decision exists. It must never be presented inside the chat composer, stream title, follower/chat-access rules, or creator-support actions. |

## Public category-browse observations

Twitch’s public Browse route separates high-level modes (Games, IRL, Music & DJs, Creative, Esports), then offers distinct **Categories** and **Live Channels** tabs, a searchable category/tag field, and a sort control. Category cards show artwork, category name, current viewers, and lightweight taxonomy. This hierarchy makes it possible to switch between a topic-first path and a creator/live-channel-first path without treating the two as the same ranking problem.

A visibly labelled display placement was shown above/alongside category content. It remained distinct from category cards and included a visible ad marker, a dedicated feedback control, and a CTA outside the organic content component. The page also retained an active mini-player state from the previously viewed stream, allowing browsing while maintaining playback context. This is a useful transferable pattern only if Kryv treats mini-player playback, browsing state, and advertising as separate modules with separate authorization and error boundaries.

### Additional Kryv Live requirements

| Area | Original Kryv requirement |
|---|---|
| Category browse | Provide top-level modes, category/channel result modes, search, server-backed filters/sorts, typed pagination, and transparent zero-result recovery. |
| Taxonomy | Define canonical owned category, tag, language, maturity, and game/topic references. Do not allow arbitrary user strings to become policy-relevant targeting categories. |
| Mini-player | Keep a provider-authorized mini-player route state, with explicit close/expand controls and no implicit autoplay of new content as a user browses. |
| Display ads | Place future feed/browse advertising only as a discrete `AdSlot` outside organic card grid semantics. Include persistent disclosure, advertiser identity, feedback/report path, safe CTA routing, policy context, and a no-fill state. |
| Ads and browsing | A failed, declined, or disabled decision cannot block category search, sort, content cards, or mini-player continuity. |
