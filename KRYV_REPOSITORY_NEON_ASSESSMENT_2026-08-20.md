## Executive assessment

Kryv has a credible modular foundation: a TypeScript/pnpm workspace, Express API, React/Vite client, Drizzle/PostgreSQL data layer, FastPix media integration, Redis-capable realtime and queue components, and intentionally disabled high-consequence payout and custody capabilities. The production health contract responds successfully, external webhook handling is designed around raw-body verification, and sensitive money-movement execution is hard-disabled. [1] [2] [3]

The principal risk is **not current database size or lock contention**. It is the combination of an application that authenticates with long-lived, script-readable JWTs, a database whose production role owns every table and has no row-level security, and a migration/recovery process that has drifted between source, production, documentation, and a soon-expiring Neon staging branch. These conditions increase the blast radius of a browser-token compromise, leaked database credential, or hurried production schema change. [4] [5] [6]

> **Overall judgment: Conditional release readiness.** Public playback/control-plane functions appear deliberately guarded, and production is responding. However, the platform should not expand privileged features, customer-wallet custody, provider payouts, advertising settlement, or multi-operator administration until the identity/session, database least-privilege, migration governance, and recovery gaps below are closed.

## Architecture and implementation overview

Kryv is organized as a pnpm workspace with an Express API (`artifacts/api-server`), a React/Vite client (`artifacts/blyze`), shared API-contract packages, and a Drizzle PostgreSQL package. The current Render topology describes separate web, realtime, and worker processes plus isolated cache and durable-queue key-value services. The use of a managed media provider and a separated asynchronous worker is directionally appropriate for a streaming product. [1] [10]

The server applies Helmet, CORS, request limits, raw parsers for webhooks, token attachment, and a production-only JWT-secret guard. It also uses provider signature verification before FastPix state changes and HMAC verification for Plisio callbacks. These are meaningful baseline controls. [2] [8]

| Strength                                               | Why it matters                                                                                                                    |
| ------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------- |
| Typed workspace boundaries and Drizzle data layer      | Reduces interface drift relative to an untyped monolith, provided the schema and migration process remains authoritative. [1] [5] |
| Raw-body webhook parsers before JSON parsing           | Preserves the signed payload necessary for callback integrity validation. [2]                                                     |
| Explicit hard-disable of provider withdrawal execution | Prevents accidental release of provider payouts despite the existence of payout code. [8]                                         |
| Redis-backed rate-limit design with local fallback     | Adds protection against brute-force and abusive request patterns; shared-state configuration remains operationally important. [2] |
| Live service health and capability disclosure          | Supports safer rollout gates and correctly reports that high-consequence capabilities are disabled. [3]                           |

## Prioritized findings

### P0 — Immediate action

No externally exploitable P0 condition was demonstrated through the read-only assessment. In particular, the public production debug route returned HTTP 401 without a bearer token, provider withdrawals report disabled, and the production database had no observed blocking locks. These are positive point-in-time observations, not a substitute for continuous monitoring. [2] [3] [6]

### P1 — Resolve before privileged-feature expansion

| ID    | Finding                                                                                                    | Evidence and impact                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                | Required remediation                                                                                                                                                                                                                                                                                                                                                                                    |
| ----- | ---------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| P1-01 | **Public signup can grant the platform-owner role by username.**                                           | The signup handler assigns `owner` whenever a registrant supplies the hard-coded `FanoDGC` username; login later reasserts that role. The production aggregate shows this reserved username is currently occupied, which reduces immediate exposure but does not fix the unsafe authorization model. A deletion, restore mistake, non-production clone, or identity-change path could convert a public registration into administrative access. [4] [6]                                                                                            | Remove username-derived authorization. Bootstrap the initial owner through a controlled migration or out-of-band administrative procedure; use an immutable user ID or explicit RBAC assignment table; reserve protected names; add a regression test proving that public registration can never create an owner. Rotate `JWT_SECRET` after deployment.                                                 |
| P1-02 | **Long-lived bearer tokens are kept in browser-accessible persistent storage without visible revocation.** | API tokens are signed for 30 days, and the client persists the token through Zustand’s default browser storage. Token validation checks signature only; the reviewed code contains no central token-version, logout, password-reset, ban, or role-change invalidation mechanism. A successful XSS or local-device compromise therefore has a long replay window, including for owner tokens. [4] [5]                                                                                                                                               | Use short-lived access tokens and rotation-backed refresh sessions, preferably secure `HttpOnly`, `Secure`, `SameSite` cookies for browser sessions. Add per-user session/token versioning and validate current role, ban status, and session state for sensitive requests. Remove the temporary acceptance of primary API tokens at the realtime gateway after migration.                              |
| P1-03 | **Production database access lacks defense in depth.**                                                     | Direct Neon inspection showed public connections are not blocked, no IP allowlist is configured, the production primary branch is unprotected, RLS is disabled on all 83 public tables, and `neondb_owner` holds every table privilege. The repository’s runtime DB layer takes a single `DATABASE_URL`, and deployment guidance identifies the owner connection role. This can be workable for a trusted server-only architecture, but a leaked connection string becomes a full-database incident rather than a narrowly scoped one. [5] [6] [7] | Create a non-owner `kryv_app` role with only required privileges; use a separate migration role; rotate any owner connection string used by the application; restrict network paths using Neon/hosting private networking or narrowly scoped ingress where feasible; protect the production branch; consider RLS for data domains where it supplies a meaningful second boundary.                       |
| P1-04 | **Schema governance has material drift and a soon-expiring unrepresented branch.**                         | Production has 83 tables while active Drizzle definitions declare 82; `creator_payment_accounts` exists only in migrations/production and is intentionally described as legacy. A Neon staging branch expires on August 21, 2026 and contains five additional objects—`ad_campaign_exception_requests`, `ad_creator_earnings`, `ad_creator_preferences`, `ad_delivery_events`, and `ad_reporting_periods`—plus nine indexes. None appears in code or migration files beyond a high-level architecture mention. [5] [6] [11]                        | Before the branch expires, preserve its schema diff and decide explicitly to discard or formalize it. Do **not** merge it blindly. Bring every retained production table under the active Drizzle schema, or archive/remove it through a reviewed migration. Replace ad-hoc production `push` workflow with versioned migration execution and a CI schema-drift check against a disposable Neon branch. |
| P1-05 | **Recovery objective is inconsistent with a commerce-capable control plane.**                              | Connected Neon project history retention is 21,600 seconds (**6 hours**), and the only named branch carrying pending accounting controls is temporary/unprotected. Six hours may be acceptable for a hobby prototype but is weak for payment, rights, moderation, and audit data where an error may be identified after the recovery window. [6]                                                                                                                                                                                                   | Define RPO/RTO explicitly; increase retention to match that policy; test point-in-time restore and branch recovery; protect production; keep migration artifacts and a verified restoration runbook in source control.                                                                                                                                                                                  |

## Secure design observations

The codebase contains several practices worth retaining. Provider callbacks use raw-body parsing before the general JSON parser; Plisio verification uses an HMAC comparison; FastPix events are handed to the provider SDK’s verified unwrap routine; and payout execution is compiled with a constant false runtime gate. The production health endpoint also explicitly states that custody, scheduled payout requests, and advertising delivery are disabled. [2] [3] [8]

The code should retain these safety gates while tightening identity. In particular, replacing the fixed owner username with explicit RBAC should not weaken the owner-only middleware or the audit logging already used by the Cinema/administration paths. The recommended change is to make user identity and role assignments revocable and database-authoritative, rather than deriving permanent authority from a display name inside application code. [4] [13]

### Before enabling commerce, custody, ads, or multiple operators

Treat the following as non-negotiable release gates: durable shared cache/queue confirmation, protected production database branch, recovery drill, least-privilege runtime DB role, short-lived/revocable sessions, explicit operator RBAC, webhook replay/idempotency tests, reconciliation runbooks, and owner/admin action audit review. The current code wisely reports these high-consequence functions disabled; that boundary should remain in place until the gates are demonstrably satisfied. [3] [8]
